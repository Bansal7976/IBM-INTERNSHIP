SLIDE 2Problem Statement & Research Gaps

Krish Manwani — speaks entire slide

Sir, autonomous driving is not a single problem — it is five separate computer vision problems that need to work together in real time. Let me explain each:

Problem 1 — Object Detection: The car must detect vehicles, pedestrians, cyclists at all times — day, night, rain, fog — and decide where they are in 3D space, not just a flat image.

Problem 2 — Lane Detection: The car must know where the road lanes are so it stays in its lane. This sounds simple, but lanes can be faded, curved, or partially blocked by other vehicles.

Problem 3 — Monocular Depth: LiDAR sensors cost ₹10–40 lakhs. We want to estimate how far away objects are using only a regular camera — this is called monocular depth estimation.

Problem 4 — Collision Prediction: Knowing an object exists is not enough — we must know how much time we have before a collision. This is called Time-to-Collision, or TTC.

Problem 5 — Real-time constraint: All of this must run faster than 30 frames per second, otherwise the car reacts too slowly to be safe.

What are Research Gaps? — How to Explain

Say: "After reviewing 15 papers in this field, we found five major things that nobody has done yet — these are called research gaps. Our project specifically targets these gaps."

  • G1: Every paper solves one task in isolation. Nobody combines all tasks into one system.
  • G2: Camera-only 3D detection scores 56.9 NDS, LiDAR+Camera scores 72.9 NDS — 16-point gap. No paper explains this gap with a controlled experiment.
  • G3: Depth estimation and object tracking have never been combined to calculate Time-to-Collision.
  • G4: Grounding DINO — a powerful open-vocabulary detector — has never been tested on real driving data.
  • G5: There's no single metric to evaluate all ADAS tasks together.
Transition (Vishal takes over): "To understand these gaps, let us walk through the 15 papers we studied."

Group 1 — 2D Object Detection (Papers 06, 07, 08)

YOLOv11  Ultralytics 2024  Paper 08 — WE USE THIS

What it solves: Detect cars, pedestrians, cyclists from a camera in real time.
How it works: YOLO stands for "You Only Look Once." The image is divided into a grid. Each grid cell simultaneously predicts bounding boxes and class probabilities in one pass — making it extremely fast. Version 11 has 22% fewer parameters than v8 while achieving 54.7 mAP (mean Average Precision) on the COCO benchmark.
Key number: 54.7 mAP — state of the art for a real-time single-stage detector.
What it misses: It only gives 2D bounding boxes in the image. It cannot tell you how far away an object is in 3D space.
Why we chose it: Best balance of speed and accuracy for our pipeline. No peer-reviewed publication yet — that's a limitation we noted.

RT-DETR  CVPR 2024  Paper 06

What it solves: Real-time detection using transformers — no NMS required.
How it works: Traditional detectors like YOLO generate hundreds of overlapping boxes and use Non-Maximum Suppression (NMS) to remove duplicates. RT-DETR uses cross-attention in a transformer to directly predict unique boxes — eliminating NMS. This makes it faster and end-to-end trainable. Achieves 53.1 AP at 108 FPS.
What it misses: Higher GPU memory than YOLO — harder to deploy on embedded devices.

YOLOv10  NeurIPS 2024  Paper 07

What it solves: NMS-free YOLO variant — simpler deployment.
How it works: Adds a dual-label assignment strategy so the model directly learns to predict unique boxes during training, removing NMS at inference. 46.3 AP with 25% fewer parameters than v8.
What it misses: Optimization of NMS-free training is complex — not fully understood yet.

Group 2 — 3D Bird's-Eye-View Detection (Papers 01, 02, 04, 05, 14)

What is BEV — Bird's Eye View?

Say: "Sir, when you look at a camera image, you see the world from the front. But for autonomous driving, we need a top-down map view — like Google Maps — showing exactly where each object is in 3D space. This is called Bird's Eye View, or BEV perception. It gives us X, Y, Z coordinates of every object relative to the car."

BEVFormer  ECCV 2022  Paper 01 — WE TRAIN THIS

What it solves: 3D object detection using only cameras — no LiDAR.
How it works: Uses a transformer with spatial cross-attention and temporal self-attention. Spatial attention looks at 6 camera views and maps image features to a 3D BEV grid. Temporal attention "remembers" the BEV from previous frames, giving the model a moving map of the scene over time. This is like the model building a mental map of the road that updates every frame.
Key number: 56.9 NDS (nuScenes Detection Score) — best camera-only result at time of publication.
What it misses: 56.9 NDS vs 72.9 for LiDAR — camera images degrade in low light, rain, and glare. It cannot measure exact distances.

BEVFusion  ICRA 2023  Paper 02 — WE TRAIN THIS

What it solves: 3D detection using BOTH camera AND LiDAR fused together.
How it works: Camera provides rich appearance and texture information. LiDAR provides precise 3D point clouds — exact distances. BEVFusion converts both modalities to a shared BEV feature map and fuses them. Camera features fill in appearance details; LiDAR features fill in exact geometry. Together they achieve much higher accuracy.
Key number: 72.9 NDS — 16 points better than BEVFormer.
What it misses: Requires expensive LiDAR sensors. Also needs precise geometric calibration between LiDAR and cameras — a hardware dependency.

Sparse4D v3  arXiv 2023  Paper 04

What it solves: Camera-only 3D detection with strong temporal modeling.
How it works: Maintains sparse 3D anchor points across frames (instead of a dense BEV grid). Uses these temporal anchors to track object positions across time — giving velocity estimates even for objects that are partially occluded. Gets 56.1 NDS with strong AMOTA (tracking) scores.
What it misses: Very high training cost — requires many GPUs and long training time.

StreamPETR  ICCV 2023  Paper 05

How it works: Propagates 3D object queries across time frames using temporal attention — "streaming" detection. Achieves 67.6 NDS with strong tracking scores.
What it misses: Latency increases with temporal dependency chain length.

DETR3D  CoRL 2022  Paper 14

How it works: Uses sparse 3D reference points to sample features from camera images. No explicit BEV grid construction — more memory efficient. 42.5 NDS.
What it misses: No temporal modeling — single frame only. Lower accuracy than BEVFormer.

Group 3 — Multi-Object Tracking (Paper 03)

ByteTrack  ECCV 2022  Paper 03 — WE USE THIS

What it solves: Track every moving object — assign it a unique ID, maintain that ID across frames, estimate its velocity.
How it works: Most trackers throw away detection boxes with low confidence scores (e.g., score < 0.5) because they might be false positives. ByteTrack's key insight: keep every detection box, even low-scoring ones. Use Hungarian algorithm to associate ALL detections (high + low score) with existing tracks. Low-confidence boxes often correspond to partially occluded objects — if you discard them, you lose the track. This gives 80.3 MOTA and 77.3 IDF1 on MOT17 — state of the art.
Why it matters for us: ByteTrack gives us per-object velocity vectors. Combined with depth from Depth Anything V2, we can calculate TTC (Time-to-Collision). This is our novel contribution.
What it misses: No Re-Identification (ReID) features — in dense crowds, it can lose tracks when two people are close together.

Group 4 — Lane Detection (Papers 09, 10)

Ultra-Fast Lane Detection v2  IEEE TPAMI 2022  Paper 10 — WE USE THIS

What it solves: Detect road lanes at extremely high speed.
How it works: Instead of detecting lane pixels one-by-one (slow), UFLDv2 frames lane detection as a row-wise classification problem. The image is divided into rows. For each row, the model classifies which column position the lane occupies. This is a global structural approach — the model sees the whole lane structure at once, making it very fast. 300+ FPS at 96.4% accuracy on TuSimple.
What it misses: Fixed grid resolution — struggles with extremely sharp curves or lanes at unusual angles not seen during training.

CLRNet  CVPR 2022  Paper 09

How it works: Cross-Layer Refinement Network. Detects lane proposals at low resolution (coarse, fast) then refines them using high-resolution features. Uses features from both deep semantic layers and shallow detail layers together. 80.47 F1 on CULane — better on curved and occluded lanes.
What it misses: Still struggles with extreme curves in bad weather.

Group 5 — Depth Estimation (Paper 11)

Depth Anything V2  NeurIPS 2024  Paper 11 — WE USE THIS

What it solves: Estimate depth (distance from camera) for every pixel in a single camera image — no LiDAR, no stereo camera needed.
How it works: Trained on 62 million+ images using a combination of labeled and unlabeled data. Uses a Vision Transformer (ViT) backbone with a DPT (Dense Prediction Transformer) head. The model learns scale-invariant depth representations — meaning it can estimate metric depth (in real meters) after fine-tuning. V2 is 10× faster than V1 while achieving SOTA on NYUv2 and KITTI depth benchmarks.
Why it matters for us: We get per-pixel metric depth from a single cheap camera. Combined with ByteTrack's velocity → Time-to-Collision calculation. This is the core of our novel TTC module.
What it misses: Nighttime and tunnel scenes drop accuracy significantly — lack of texture makes depth estimation harder.

Group 6 — LiDAR 3D Detection (Papers 12, 13)

PointPillars  CVPR 2019  Paper 12

What it solves: 3D object detection from LiDAR point clouds at high speed.
How it works: LiDAR gives you a 3D point cloud — millions of XYZ points. PointPillars groups points into vertical columns called "pillars." Each pillar is encoded as a fixed-size feature vector. This converts the 3D point cloud into a 2D pseudo-image, which can be processed by a standard 2D CNN — very fast. 62 Hz on KITTI, 82.58 AP for cars.
What it misses: Grouping into pillars loses vertical (Z-axis) structure — can't distinguish objects stacked vertically.

VoxelNet  CVPR 2018  Paper 13

How it works: Divides 3D space into voxels (3D cubes). Applies a Voxel Feature Encoding layer inside each voxel to capture 3D structure. More accurate than PointPillars but much more memory-intensive and slow — not real-time at scale.

Group 7 — Open-Vocabulary Detection (Paper 15)

Grounding DINO  ECCV 2024  Paper 15 — WE BENCHMARK THIS

What it solves: Detect ANY object described in natural language — not just pre-defined classes.
How it works: Combines a DINO visual backbone with BERT text encoder. Given a text prompt like "yellow school bus" or "construction worker in orange vest," it uses cross-modal attention to find that object in the image. 52.5 AP zero-shot on COCO — without seeing COCO training data. Can detect things traditional detectors can never detect because they weren't in the training classes.
Our contribution: Nobody has tested Grounding DINO on KITTI or nuScenes. We will establish the first baseline — does open-vocabulary detection work for autonomous driving?
What it misses: Slower than YOLO. Has never been evaluated on driving datasets. Our work closes this gap.
Vishal — Literature Review Closing

So sir, to summarize: across all 15 papers, no one has combined these tasks into a single pipeline. No one has used depth + tracking for collision prediction. No one has tested Grounding DINO on driving data. These are exactly the gaps we are addressing.

Transition (Krish takes over): "Now let me explain the architecture we designed to address all these gaps."

SLIDE 4Proposed Architecture

Krish Manwani

Sir, our pipeline takes a camera video as input and passes it through five sequential stages.

Stage 1 — YOLOv11: Detects all objects in the frame — gives 2D bounding boxes with class labels (car, pedestrian, cyclist). This runs at 30+ FPS.

Stage 2 — Ultra-Fast Lane v2: Runs in parallel with YOLOv11. Detects road lane boundaries at 300 FPS — the output is a lane overlay on the image showing safe driving region.

Stage 3 — Depth Anything V2: Also runs in parallel. Takes the same camera frame and produces a depth map — every pixel gets a distance value in meters. So now we know how far away each detected object is.

Stage 4 — ByteTrack: Takes the YOLOv11 bounding boxes and tracks each object across frames — assigns unique IDs and computes per-object velocity (how fast each object is moving toward or away from us).

Stage 5 — TTC Calculator: Our novel module. Formula: TTC = Distance ÷ Relative Velocity. Distance comes from Depth Anything V2. Velocity comes from ByteTrack. Output: a collision risk alert — "Object #3 will collide in 2.4 seconds."

3D Branch — Explain This When Asked

Say: "In parallel, we also train a 3D perception branch. BEVFormer trains on nuScenes using only cameras to get 3D detection. BEVFusion trains the same dataset using cameras + LiDAR. We compare their results to quantify exactly how much LiDAR improves accuracy — this directly addresses Gap G2 that no paper has done systematically."

Export Pipeline

Say: "After training, we export the models to multiple deployment formats: ONNX for cross-platform compatibility, TensorRT for 3–5× GPU speedup, CoreML for Apple devices, and OpenVINO for Intel edge hardware. This makes the system deployable on real vehicles — not just a research demo."

SLIDE 5Tech Stack & Datasets

Vishal Bansal

Sir, for the technology stack — we use PyTorch as the core deep learning framework. MMDetection3D provides ready-to-use implementations of BEVFormer, BEVFusion, and PointPillars — so we can train these research models without reimplementing them from scratch. Ultralytics provides the YOLOv11 implementation. Albumentations handles data augmentation.

For deployment: all models are exported to ONNX first, then optimized using TensorRT for our target GPU — giving 3–5× speedup over PyTorch inference.

For datasets:

KITTI — the standard benchmark for 2D and 3D detection. 7,481 training frames, 8 object classes, captured in Karlsruhe, Germany. Comes with stereo cameras and a LiDAR — we use this for 2D detection and LiDAR experiments.

nuScenes — the industry standard for BEV 3D detection. 28,000+ annotated frames, 6 cameras covering full 360 degrees, LiDAR, radar. Covers Boston and Singapore driving conditions. This is the dataset BEVFormer and BEVFusion are evaluated on.

TuSimple & CULane — the two standard lane detection benchmarks. TuSimple is highway driving with clear lanes. CULane covers urban, highway, and challenging conditions — 88,000 training frames.

Transition (Krish takes over): "Now let me explain how we are training these models and what performance we expect."

SLIDE 6Training Strategy & Expected Results

Krish Manwani

Sir, models like BEVFormer and BEVFusion are too large to train on a single GPU. We use an HPC (High-Performance Computing) cluster with a SLURM job scheduler — this lets us distribute training across 32 GPUs simultaneously.

We use PyTorch DDP — Distributed Data Parallel. Each GPU trains on a different batch of data, computes gradients independently, and all GPUs synchronize gradients after each batch using NCCL all-reduce. This is equivalent to training with a batch size 32× larger than a single GPU allows.

We also use mixed precision training (AMP) — computations use 16-bit floats where possible instead of 32-bit. This gives approximately 2× speedup and reduces memory usage by 40%.

For expected results — sir, these are our targets:

YOLOv11 on KITTI: ≥85% mAP. BEVFormer on nuScenes: ≥50 NDS. BEVFusion: ≥70 NDS. UFLDv2 on TuSimple: ≥96% accuracy. Our TTC system: end-to-end latency under 50 milliseconds on an RTX 3090.

If Asked: What is NDS?

NDS = nuScenes Detection Score. It is a composite metric that combines: detection accuracy (mAP), translation error, scale error, orientation error, velocity error, and attribute error. A score of 72.9 means the model gets 72.9% of these metrics right on average — much harder to achieve than simple mAP.

SLIDE 7Contributions

Vishal Bansal

Sir, our five specific contributions — each directly closes one of the research gaps we identified:

Contribution 1 — Unified 5-task pipeline: We are the first to combine object detection, lane detection, depth estimation, tracking, and TTC in a single open-source inference graph. This closes Gap G1.

Contribution 2 — Novel TTC module: We combine ByteTrack's per-object velocity with Depth Anything V2's metric depth to compute real-time Time-to-Collision. No prior work has done this combination. This closes Gap G3.

Contribution 3 — Grounding DINO on driving data: We are the first to evaluate Grounding DINO on KITTI and nuScenes — establishing a zero-shot detection baseline for autonomous driving. This closes Gap G4.

Contribution 4 — Controlled camera vs LiDAR comparison: BEVFormer vs BEVFusion trained under identical HPC conditions — same dataset, same training setup. This gives a fair comparison and directly quantifies the benefit of LiDAR, closing Gap G2.

Contribution 5 — Open-source HPC pipeline: Full codebase with SLURM scripts, DDP training, and model export tools — reproducible by any research group, closing the tooling gap G1.

Likely Questions & How to Answer

QuestionWho AnswersAnswer
Why not just use LiDAR for everything? Krish LiDAR costs ₹10–40 lakhs per unit — not scalable for mass market vehicles. Our camera-first approach using Depth Anything V2 gives 80–90% of the accuracy at 5% of the cost. BEVFusion shows us exactly how much we lose without LiDAR — 72.9 vs 56.9 NDS.
What is BEV and why is it important? Vishal BEV = Bird's Eye View — a top-down map of the scene. It tells us the exact X, Y, Z position of every object relative to the car. For path planning, the car needs to know "the pedestrian is 4 meters ahead and 1 meter to the left" — not just "there's a pedestrian in the image." BEV gives spatial coordinates, not just image coordinates.
How is your TTC calculation novel? Krish TTC = Distance / Relative Velocity. Previous work either used LiDAR for distance (expensive) or did not combine it with tracking. We use Depth Anything V2 to get monocular depth (no LiDAR) and ByteTrack to get velocity — and combine them. Paper 11 and Paper 03 were never integrated before. This is our first contribution.
What does 56.9 NDS mean in real terms? Vishal NDS measures five aspects of detection quality — position accuracy, size accuracy, orientation, velocity estimation, and object attributes. 56.9 means the model correctly handles ~57% of these criteria on average across all objects in the nuScenes test set — which is quite challenging because it includes night, rain, and diverse urban environments.
Why SLURM / HPC? Can't you train on Colab? Krish BEVFormer training takes 24+ hours on 8 A100 GPUs. BEVFusion is similar. Google Colab disconnects after 12 hours and has only 1 GPU. HPC with SLURM lets us schedule 32 GPU jobs that run continuously — reducing training time from weeks to hours. DDP across 32 GPUs gives us effective batch sizes impossible on consumer hardware.
What is Grounding DINO — how is it different from YOLO? Vishal YOLO can only detect object classes it was trained on — e.g., car, person, bicycle. If there is an unusual object — like a "broken traffic cone" or "parked ambulance with doors open" — YOLO misses it because it wasn't in training classes. Grounding DINO takes a text prompt and finds anything described. This is critical for edge cases in autonomous driving that fixed-class detectors miss.

Glossary — If Sir Asks "What Does This Mean?"

TermSimple Explanation
mAPMean Average Precision — how accurately the model detects objects. 0–100%, higher is better.
NDSnuScenes Detection Score — composite metric measuring 3D detection quality on nuScenes dataset.
BEVBird's Eye View — top-down map of the scene showing exact 3D positions of all objects.
TTCTime-to-Collision — how many seconds before the car hits an object. TTC = Distance ÷ Speed.
LiDARSensor that shoots laser pulses and measures their return time to get exact 3D distances. Very accurate but expensive.
Monocular DepthEstimating distance from a single regular camera — without LiDAR or stereo cameras.
DDPDistributed Data Parallel — training a model on multiple GPUs simultaneously to speed up training.
SLURMJob scheduler for HPC clusters — queues and manages GPU training jobs.
NMSNon-Maximum Suppression — removes duplicate overlapping detection boxes. RT-DETR and YOLOv10 eliminate the need for this.
ONNXOpen Neural Network Exchange — a common format to export trained models so they run on any hardware.
TensorRTNVIDIA's optimization library — converts ONNX models to run 3–5× faster on NVIDIA GPUs.
AMPAutomatic Mixed Precision — uses 16-bit math where safe to speed up GPU training by ~2×.
Transformer / AttentionNeural network architecture that lets each part of the image "attend to" (look at) every other part — better at understanding context than older CNN models.
Zero-shotTesting a model on data it was never trained on — measures how well it generalizes.
Voxel3D equivalent of a pixel — a small cube in 3D space. LiDAR point clouds can be divided into voxels.
